Observability guide

Tracing LangChain, LangGraph and DeepAgents with a local Langfuse

Run Langfuse on your own machine with Docker Compose, then trace whatever you are building. All three frameworks share one integration path — LangChain's callback system — so you set Langfuse up once and pass the same handler to a chain, a graph, or a deep agent.

run docker compose up host http://localhost:3000 sdk langfuse python v3

1. Run Langfuse locally

The fastest way to get an instance on your own machine. You need git and Docker with Compose — Docker Desktop covers both on macOS and Windows.

  1. Clone the repository

    bash
    git clone https://github.com/langfuse/langfuse.git
cd langfuse

  2. Start the stack

    This pulls the web app, worker, Postgres, ClickHouse, Redis and MinIO, then wires them together.

    bash
    docker compose up

  3. Wait for it to be ready

    First boot takes two to three minutes while migrations run. Watch for the langfuse-web-1 container logging Ready.

  4. Open the UI

    http://localhost:3000

    Langfuse is now running locally.

Stopping it

How you started itHow to stop it
Foreground, no -d flag Press Ctrl+C in that terminal
Background, with -d docker compose down
bash
docker compose down      # stop, keep your traces
docker compose down -v   # stop and delete the volumes — all data goes with them

Local use only. This setup runs on the default secrets shipped in docker-compose.yml. Replace them before putting an instance anywhere other than your own machine — see the self-hosting docs for production deployments.

2. Create the Langfuse project

Langfuse groups traces by project, and each project carries its own key pair. Do this once — all three frameworks report into the same project.

  1. Sign up

    On the instance you just started, create an account with email and password, or through the SSO provider you configured on the container. The first account you create owns the instance.

  2. Create a project

    • Select an organization, or click New Organization if this is a fresh instance.
    • Inside it, click New Project.
    • Name it something you will recognise in the trace list — agents-tracing works.

  3. Copy the API keys

    Open Project Settings → API Keys and click Create new API key. Three values appear:

    Public key

    Starts with pk-lf-

    Secret key

    Starts with sk-lf-

    Host URL

    http://localhost:3000 when self-hosted

    Copy the secret key now. Langfuse displays it once. If you lose it, delete the key pair and create a new one.

3. Shared setup

Identical for LangChain, LangGraph and DeepAgents. Everything after this section is framework-specific.

This guide targets Python SDK v4, which introduced an observations-first data model: user, session, tags and metadata propagate to every observation rather than living only on the trace. Check yours with pip show langfuse.

Two things moved in v4 that older examples still show: update_current_trace() became propagate_attributes(), and CallbackHandler(update_trace=...) was removed. Anything importing langfuse.callback is v2, two majors back — current is langfuse.langchain.

  1. Install dependencies

    Install langfuse plus whichever framework you are using. The examples below use Anthropic models and Tavily search.

    bash
    # shared
pip install langfuse langchain langchain-anthropic

# add per framework
pip install langgraph          # LangGraph example
pip install deepagents tavily-python   # DeepAgents example

  2. Set environment variables

    Because Langfuse runs locally, the base URL points at your own machine rather than a cloud region.

    python
    import os

# Langfuse credentials (from your project settings)
os.environ.setdefault("LANGFUSE_PUBLIC_KEY", "pk-lf-...")
os.environ.setdefault("LANGFUSE_SECRET_KEY", "sk-lf-...")
os.environ.setdefault("LANGFUSE_BASE_URL", "http://localhost:3000")  # local self-hosted instance

# Model and tool keys used by the examples
os.environ.setdefault("ANTHROPIC_API_KEY", "sk-ant-...")
os.environ.setdefault("TAVILY_API_KEY", "tvly-...")

  3. Initialize the client and handler

    Create the handler once and reuse it. The auth check is worth keeping while you set up — it fails loudly on a wrong key or an unreachable host, instead of dropping traces quietly.

    python
    from langfuse import get_client
from langfuse.langchain import CallbackHandler

# Initialize Langfuse client (singleton, reads the env vars above)
langfuse = get_client()

# Verify connection
if langfuse.auth_check():
    print("Langfuse client is authenticated and ready!")
else:
    print("Authentication failed. Please check your credentials and host.")

# One handler, reused across chains, graphs and agents
langfuse_handler = CallbackHandler()

4. One example per framework

Langfuse hooks into LangChain callbacks, the standard mechanism for observing LangChain execution. LangGraph is built on LangChain runnables and DeepAgents is built on LangGraph, so the same handler flows all the way down without extra instrumentation.

the one line that matters
config={"callbacks": [langfuse_handler]}

What changes between frameworks is only what you attach it to, and how deep the resulting trace tree goes.

FrameworkYou attach it toTrace depth you get
LangChain chain.invoke(...) Prompt, model generation, parser — one level of runnables
LangGraph graph.invoke(...) or graph.stream(...) One span per node, plus every model call inside it
DeepAgents agent.invoke(...) Planning, tool calls, and sub-agents nested under the parent

Pick your framework below. Each example runs on its own once the shared setup above has been executed.

A LangChain chain

The simplest case: a prompt piped into a model. Pass the handler in the invocation config and Langfuse records the prompt, the generation, token counts, and latency.

python
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

llm = ChatAnthropic(model="claude-sonnet-4-5", temperature=0.2)
prompt = ChatPromptTemplate.from_template(
    "Explain {topic} to a backend engineer in three sentences."
)

chain = prompt | llm | StrOutputParser()

# Tracing happens here
answer = chain.invoke(
    {"topic": "LLM observability"},
    config={"callbacks": [langfuse_handler]},
)

print(answer)

Roughly what lands in Langfuse

trace
TRACE  RunnableSequence
├─ SPAN        ChatPromptTemplate
├─ GENERATION  ChatAnthropic     tokens · latency · cost
└─ SPAN        StrOutputParser

Each invoke creates its own trace. To group several calls into one, wrap them in langfuse.start_as_current_observation(...) — see grouping traces.

A LangGraph graph

Same pattern, one level deeper: each node becomes its own span, so you can see which node looped, retried, or burned the tokens. stream takes the same config as invoke.

python
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph
from langgraph.graph.message import add_messages
from langchain_anthropic import ChatAnthropic

class State(TypedDict):
    messages: Annotated[list, add_messages]

llm = ChatAnthropic(model="claude-sonnet-4-5")

def chatbot(state: State):
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(State)
builder.add_node("chatbot", chatbot)
builder.set_entry_point("chatbot")
builder.set_finish_point("chatbot")
graph = builder.compile()

# Tracing happens here
result = graph.invoke(
    {"messages": [{"role": "user", "content": "What is Langfuse?"}]},
    config={"callbacks": [langfuse_handler]},
)

print(result["messages"][-1].content)

Attach the handler once instead

If the graph is invoked from several places, bind the callback to the compiled graph and stop repeating the config.

python
graph = builder.compile().with_config({"callbacks": [langfuse_handler]})

graph.invoke({"messages": [{"role": "user", "content": "What is Langfuse?"}]})

Roughly what lands in Langfuse

TRACE  LangGraph
└─ SPAN        chatbot
   └─ GENERATION  ChatAnthropic     tokens · latency · cost

Every invocation is a separate trace, even when the graph keeps state across turns. Pass the LangGraph thread_id as langfuse_session_id so a conversation reads as one session in the UI — see session IDs.

A DeepAgent

DeepAgents plans, calls tools, and can delegate to sub-agents. All of it is nested under one parent trace, which is where tracing pays for itself — a long research run is otherwise hard to follow.

python
from typing import Literal
from tavily import TavilyClient
from deepagents import create_deep_agent

tavily_client = TavilyClient(api_key=os.environ["TAVILY_API_KEY"])

def internet_search(
    query: str,
    max_results: int = 5,
    topic: Literal["general", "news", "finance"] = "general",
    include_raw_content: bool = False,
):
    """Run a web search"""
    return tavily_client.search(
        query,
        max_results=max_results,
        include_raw_content=include_raw_content,
        topic=topic,
    )

research_instructions = """You are an expert researcher. Your job is to conduct
thorough research, and then write a polished report.

You have access to an internet search tool as your primary means of gathering
information.
"""

agent = create_deep_agent(
    tools=[internet_search],
    system_prompt=research_instructions,
)

# Tracing happens here
result = agent.invoke(
    {"messages": [{"role": "user", "content": "What is Langfuse and how does it help with LLM observability?"}]},
    config={"callbacks": [langfuse_handler]},
)

Sub-agents need no extra setup

Pass subagents at creation and each delegated run appears nested inside the same trace.

critique_sub_agent = {

}

agent = create_deep_agent(
    tools=[internet_search],
    system_prompt=research_instructions,
    subagents=[critique_sub_agent],
)

5. Choosing how to instrument

The callback handler covers everything LangChain runs and nothing else. The moment your own code matters — a vector search, an HTTP fetch, a guardrail, a parser — you pick one of three tools. They are interoperable and nest automatically, so mixing them in one trace is normal.

ToolReach for it whenWhat it cannot do
Callback handler
CallbackHandler()		 Anything LangChain, LangGraph or DeepAgents executes See your own functions, or any call that is not a LangChain runnable
Decorator
@observe()		 A function of yours that should be one span Trace part of a function, or work that spans two functions
Context manager
start_as_current_observation()		 A block inside a function, or a parent that owns the whole turn Cover code that is not in one contiguous block
Manual
start_observation()		 Work whose start and end are far apart Become the active parent — nothing nests under it automatically

Quick decision. Is it a LangChain runnable? Nothing to do. A whole function of yours? @observe. Part of a function, or you need the trace id or the outcome? with. Start and end in different places? Manual.

The decorator — one function, one span

@observe() wraps a function and records its arguments, return value, duration and any exception. Nesting follows your call hierarchy with no extra work, and because it reads the active context, a decorated function called from inside a traced node lands in the right place automatically.

Use it for retrieval, reranking, document parsing, a call to another service — the steps that explain a bad answer. Skip it for anything LangChain already traces, and for bookkeeping like audit writes or cache puts, which only add noise.

python
from langfuse import observe

@observe(name="qdrant-search")
async def retrieve(query: str, top_k: int = 10):
    return await qdrant.search(query, limit=top_k)

@observe(name="rerank", capture_input=False)
def rerank(chunks, query):
    # capture_input=False because `chunks` is large. Set what you want instead.
    langfuse.update_current_span(input={"query": query, "n": len(chunks)})
    return reranker.rank(chunks, query)

It captures arguments by default. A function that takes your whole context object or a list of retrieved chunks will dump all of it into Langfuse on every call. Use capture_input=False (and capture_output=False) and set the fields you want, or disable it globally with LANGFUSE_OBSERVE_DECORATOR_IO_CAPTURE_ENABLED.

The context manager — a parent that owns the turn

start_as_current_observation() creates a span and makes it the active parent, so everything created inside it — decorated functions, LangChain runs, nested blocks — becomes its child.

You do not need one for a single invoke where you only want user, session and tags. You do need one when any of these is true:

  • Several steps must form one trace. Retrieval, then the graph, then a summariser. Without a parent they are three separate traces and the cost of one user turn is split across three rows.
  • The outcome is only known at the end. Metadata is set before the call; success, cancellation and failure are known after. A caught exception without this looks like a successful run.
  • You need the trace id during the run. get_current_trace_id() returns a value only inside an active observation. No id means no thumbs-up score later.
  • Trace input and output should be yours. They mirror the root observation by default, and LLM-as-a-judge evaluators read them.
python
with langfuse.start_as_current_observation(
    as_type="span",
    name="chat-turn",
    input={"question": question},          # becomes the trace input
) as root:

    trace_id = langfuse.get_current_trace_id()   # send this to your frontend

    try:
        chunks = await retrieve(question)         # @observe span
        answer = await graph.ainvoke(             # handler spans
            state, config={"callbacks": [langfuse_handler]}
        )
        root.update(output={"answer": answer})    # becomes the trace output

    except RequestCancelled:
        root.update(level="WARNING", status_message="cancelled by user")
        raise
    except Exception as exc:
        root.update(level="ERROR", status_message=str(exc))
        raise
resulting trace
TRACE  chat-turn                         input and output set explicitly
├─ SPAN        retrieve                  @observe
├─ SPAN        rerank                    @observe
└─ SPAN        LangGraph                 callback handler
   ├─ SPAN        preprocess
   └─ SPAN        deep_agent
      └─ GENERATION  ChatOpenAI

One trace, three instrumentation styles, no manual wiring between them.

Manual observations — the exception

Use start_observation() when a span's start and end are not in the same block: a background task kicked off by a request, or work finished by a later event. You call .end() yourself; forget it and the span never appears.

It does not shift the active context. A manual span is a child of whatever was active when you created it, but nothing created afterwards nests under it — those still attach to the original parent. So it is the wrong tool for wrapping a graph or a stream. To give it children, call start_as_current_observation() on the span object itself.

python
with langfuse.start_as_current_observation(as_type="span", name="chat-turn"):
    audit = langfuse.start_observation(name="audit-log")
    audit.update(input={"question": question})

    answer = agent.invoke(state, config={"callbacks": [langfuse_handler]})

    audit.update(output={"written": True})
    audit.end()          # required — the `with` form does this for you

One trap with streaming endpoints

If your endpoint returns a StreamingResponse, the handler returns before the generator runs. A span opened around the return closes immediately and its children orphan.

python
# Wrong — the span closes before any work happens
with langfuse.start_as_current_observation(as_type="span", name="chat-turn"):
    return StreamingResponse(event_stream())

# Right — open it inside the generator
async def event_stream():
    with langfuse.start_as_current_observation(as_type="span", name="chat-turn") as root:
        async for chunk in graph.astream(state, config=run_config):
            yield ...
        root.update(output={"answer": final_answer})

Verify nesting under concurrent load rather than assuming it: OpenTelemetry context across a suspended async generator is a known sharp edge. If you do not need non-LangChain work in the trace, skip the parent span and let the config do the work.

6. Useful attributes

Out of the box you get a tree of spans named after your runnables. That is enough to debug one run, but not enough to answer "which users cost the most" or "why did retrieval fail for that request". These attributes are what turn traces into something you can filter, cost-attribute, and build dashboards on. All of them work identically for LangChain, LangGraph and DeepAgents.

AttributeSet it withWhat it unlocks
Metadataany key in config["metadata"]Filtering by arbitrary context; input for evaluators
Model, tokens, costcaptured automaticallyCost breakdowns by model, user, feature
Tagslangfuse_tagsMetric breakdowns by business dimension

Session IDlangfuse_session_idSession replay across multiple traces
EnvironmentLANGFUSE_TRACING_ENVIRONMENTKeeps dev traces out of production dashboards

All of them at once

Everything except the environment and the prompt link can be set through the invocation config. Start here — three other approaches follow, for cases where the values are not available at the call site.

result = agent.invoke(

            "langfuse_user_id": "user-5678",     # reserved keys
            "langfuse_session_id": "thread-1234",

Four ways to set them

The reserved metadata keys above are the simplest route, but not the only one. Which fits depends on whether the values are known at build time, at call time, or somewhere deeper in your own code.

ApproachUse when
1. Metadata in the invoke config The values are known at the call site. Simplest, and what most examples show.
2. Bound once with .with_config() The values are fixed for the lifetime of the chain — app version, feature name, a static tag set.
3. propagate_attributes() around the call Several invocations share the same user or session, or you want the attributes on every nested observation.
4. @observe plus propagate_attributes() The values are only known partway through your own function, after the call has started.

2 — bind them to the chain

Stops you repeating the same config at every call site. Anything set here applies to every invocation of that runnable.

python
traced_agent = agent.with_config({
    "callbacks": [langfuse_handler],
    "metadata": {"langfuse_tags": ["research"], "app_version": "2.4.1"},
})

traced_agent.invoke({"messages": [{"role": "user", "content": "What is Langfuse?"}]})

3 — propagate around the call

The v3 way to set attributes on everything inside a scope, including observations your own code creates alongside the LangChain ones.

python
from langfuse import get_client, propagate_attributes

langfuse = get_client()

with langfuse.start_as_current_observation(as_type="span", name="chat-turn"):
    with propagate_attributes(
        user_id="user-5678",
        session_id="thread-1234",
        tags=["research"],
        metadata={"app_version": "2.4.1"},
    ):
        agent.invoke(
            {"messages": [{"role": "user", "content": "What is Langfuse?"}]},
            config={"callbacks": [langfuse_handler]},
        )

4 — set them after the fact

For values you only learn mid-request — the user id after auth resolves, a tenant after routing, a classification the first model call produced.

python
from langfuse import observe, propagate_attributes

@observe()
def handle_request(payload):
    user = authenticate(payload)          # only known now

    with propagate_attributes(
        user_id=user.id,
        session_id=payload["thread_id"],
        tags=["research"],
    ):
        return agent.invoke(
            {"messages": payload["messages"]},
            config={"callbacks": [langfuse_handler]},
        )

On v3 this was langfuse.update_current_trace(...), called imperatively rather than as a block. If you genuinely cannot use a with — a framework pre-hook, for instance — langfuse.update_current_span() still sets attributes on the active observation.

If attributes land on a child span instead of the trace. With some agent setups the metadata attaches to a nested observation rather than the parent trace, so the trace list shows nothing. Use approach 3: an enclosing span plus propagate_attributes, called early enough to cover every observation. The old CallbackHandler(update_trace=True) fix was removed in v4.

Metadata for context

Metadata is a free-form key-value store on the observation. It is the right home for anything that is useful context but does not belong in the name or the input and output. In practice that means:

  • Evaluation context — ground truth or expected behaviour that an LLM-as-a-judge evaluator needs but that is not part of the actual input. Evaluators can reference metadata fields in their variable mapping.
  • Request context — internal request IDs, the API route or app version that handled the call, active feature flags or experiment variants. This is what lets you correlate a trace with your other systems.
  • Retrieval context — for RAG steps, the data source, the index queried, how many chunks came back. Invaluable when a retrieval step returns junk.
  • Raw payloads — full request or response objects that would clutter the input and output fields but are occasionally needed.
  • Annotation context — extra information that helps a human reviewer judge the run fairly.
python
config={
    "callbacks": [langfuse_handler],

        "app_version": "2.4.1",
        "experiment_variant": "rerank_v2",
        "retrieval_source": "confluence",
        "retrieval_chunks": 8,
    },
}

Model, tokens and cost

Cost attribution needs three things on each generation observation: the model name, which Langfuse looks up in its pricing table; usage details, meaning input, output and optionally cached tokens; and cost details, only if you want to override the automatic pricing because you have a custom agreement.

All three integrations capture this for you — the LangChain callback reads it off the model response. There is nothing to write.

GENERATION ChatAnthropic claude-sonnet-4-5
1,842input tokens 1,024cached 318output tokens $0.0071cost 2.1 slatency

Generation observation. If cost shows as empty, the model name did not match Langfuse's pricing table — add a model definition under project settings and it backfills for new traces.

Tags for business dimensions

Tags drive filtering and metric breakdowns along dimensions your business cares about: how latency differs between web and API users, how cost splits across features. They are immutable and set at creation time, which makes them ideal for things you know upfront and useless for things you learn later.

python
"metadata": {"langfuse_tags": ["channel:web", "feature:report-builder"]}

If you need to label a trace based on something determined after the run — an LLM-as-a-judge verdict, a human review outcome — use scores instead. Tags cannot be edited once the trace is written.

User IDs

Setting a user ID connects traces to people and unlocks the per-user views: which users cost the most, how output quality varies between them, what one user's usage actually looks like over a week.

python
"metadata": {"langfuse_user_id": "user-5678"}

Use a stable internal identifier, not an email address or a name. The user ID is displayed throughout the UI and exported with the trace.

Session IDs

When several traces logically belong to one interaction, group them into a session and you get a replay view of the whole thing in sequence. This is worth doing when you are building a chatbot, where each user message is its own trace but the conversation is one thing; when several agents each contribute to a final output; or when a workflow spans multiple requests with human steps in between. A single-request, single-response app does not need sessions.

In LangGraph and DeepAgents the natural session id is the thread_id you are already passing.

python
thread_id = "thread-1234"

result = graph.invoke(
    {"messages": [{"role": "user", "content": "and what about pricing?"}]},
    config={
        "callbacks": [langfuse_handler],
        "configurable": {"thread_id": thread_id},   # LangGraph state
        "metadata": {"langfuse_session_id": thread_id},  # Langfuse grouping
    },
)

Environment

Set the environment so your local experiments do not pollute production dashboards and evaluations. It is a first-class field rather than metadata, and the simplest place to set it is the environment itself.

bash
export LANGFUSE_TRACING_ENVIRONMENT="development"   # or staging, production

If one shared process serves several environments, set it per request instead:

python
from langfuse import propagate_attributes

with propagate_attributes(environment="staging"):
    chain.invoke({"topic": "observability"}, config={"callbacks": [langfuse_handler]})

Linking prompts

If you manage prompts in Langfuse, link them to your generations and you can see which prompt version produced a given trace, then compare metrics across versions as you iterate.

The link goes on the prompt template, not on the invocation config — a common source of confusion, since every other attribute here goes the other way.

python
from langchain_core.prompts import ChatPromptTemplate

langfuse_prompt = langfuse.get_prompt("research-instructions")

prompt = ChatPromptTemplate.from_template(
    langfuse_prompt.get_langchain_prompt(),
    metadata={"langfuse_prompt": langfuse_prompt},   # the link
)

chain = prompt | llm
chain.invoke({"topic": "observability"}, config={"callbacks": [langfuse_handler]})
GENERATION ChatAnthropic research-instructions v4

The prompt chip on a generation links back to that version in prompt management.

Grouping several calls into one trace

Each invoke creates its own trace. To make a multi-step pipeline read as a single trace, wrap the calls in a Langfuse observation — anything the handler records inside that scope nests under it, including non-LangChain work of your own.

python
from langfuse import get_client, propagate_attributes

langfuse = get_client()

with langfuse.start_as_current_observation(as_type="span", name="research-pipeline") as root:
    root.update(input={"query": "What is Langfuse?"})

    with propagate_attributes(
        session_id="thread-1234",
        user_id="user-5678",
        metadata={"app_version": "2.4.1"},
    ):
        draft = chain.invoke({"topic": "observability"}, config={"callbacks": [langfuse_handler]})
        review = agent.invoke(
            {"messages": [{"role": "user", "content": draft}]},
            config={"callbacks": [langfuse_handler]},
        )

    root.update(output={"final": review["messages"][-1].content})

Attributes set through propagate_attributes apply to every observation created inside the block, so you set them once rather than on each invocation.

Call it early. Only observations created inside the block carry the attributes, and Langfuse computes attribute-level metrics from those. Propagated values must be strings of 200 characters or fewer, and propagated metadata keys must be alphanumeric — invalid values are dropped with a warning. Bulk context belongs in observation metadata through the invocation config, not here.

Flushing before exit

The SDK batches events in the background. A long-running service needs nothing extra, but a script that exits immediately can drop its last batch.

python
from langfuse import get_client

get_client().flush()      # wait for queued events to be sent
get_client().shutdown()   # flush and stop the background worker, at process exit

Troubleshooting

Nearly every setup problem looks the same from the outside: the run completes normally, but the trace list stays empty.

No traces appearing

  1. Turn on debug logging and run again:
    bash
    export LANGFUSE_DEBUG="True"
  2. Check that LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY and LANGFUSE_BASE_URL match the project settings. Keys from a different project fail quietly.
  3. Confirm the handler actually reached the call. A config passed to the wrong argument, or a nested chain built with its own config, silently drops the callback.
  4. Call get_client().flush() before a short-lived script exits.
  5. Read the container logs for ingestion errors: docker compose logs -f langfuse-web langfuse-worker. If the web container never logged Ready, the stack is still booting or something else holds port 3000.

Traces appear but are shallow

If a nested chain or sub-graph is missing, it was probably invoked outside the traced runnable — for example, inside a plain Python helper called by a tool. Wrap that section in a Langfuse observation, as shown under grouping traces.

Import errors on CallbackHandler

langfuse.callback is the v2 path. On v3 the import is from langfuse.langchain import CallbackHandler, the handler takes no constructor arguments, and options like sampling move to the Langfuse client or environment variables.
