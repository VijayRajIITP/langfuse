1. What is DeepEval

An open-source framework for unit-testing LLM output, built around a test case, a metric, and — optionally — a dataset.

  • 50+ ready-to-use metrics: LLM-as-judge, agent, tool-use, conversational, safety, RAG, multimodal
  • Evaluates agents, chatbots, RAG pipelines, MCP systems, and custom workflows
  • Runs end-to-end, component-level, and trajectory-based evals
  • Generates synthetic datasets for edge cases that are hard to collect by hand

Local-first. Evaluations run in your own environment — no account required. When the team wants shared dashboards, regression tracking, or production monitoring, DeepEval connects natively to Confident AI.

2. Getting started

Two paths in — pick whichever matches how the team works.

  1. Install

    bash
    pip install -U deepeval

  2. Write a test case

    python
    from deepeval import assert_test
from deepeval.metrics import AnswerRelevancyMetric
from deepeval.test_case import LLMTestCase

def test_answer_relevancy():
    metric = AnswerRelevancyMetric(threshold=0.5)
    test_case = LLMTestCase(
        input="What if these shoes don't fit?",
        actual_output="We offer a 30-day full refund at no extra cost.",
        retrieval_context=["All customers get a 30 day full refund."]
    )
    assert_test(test_case, [metric])

  3. Run it

    bash
    deepeval test run test_example.py

    Set OPENAI_API_KEY (or point at another provider) first — most metrics use an LLM judge.

Install the DeepEval Agent Skill and let Cursor, Claude Code, Codex, or Windsurf pick the right test shape, write the suite, and iterate on failures.

npx skills add confident-ai/deepeval --skill "deepeval"

Then paste the starter prompt from the Vibe Coder Quickstart and point it at your app.

3. Core building blocks

Four concepts that show up throughout DeepEval.

ConceptDefinition
Test CaseOne behavior to evaluate: input, output, expected behavior, tools, context, metadata
DatasetA collection of goldens that makes evals repeatable across prompts, models, and releases
MetricThe scoring logic that decides whether a response, trace, span, or output meets criteria
TraceA runtime record of an agent's steps, spans, inputs, outputs, tool calls, and component behavior

4. Three eval modes

Combine all three: score the black-box result, evaluate the full trajectory, then inspect spans to find failures.

ModeBest forWhat it does
End-to-endRaw LLM APIs, simple apps, chatbotsTreats the app as a black box — inputs, outputs, expected behavior, metrics
Component-levelAgents, tool-using workflows, MCP systemsTraces the app and scores individual spans, tools, retrievers, generators
Trajectory-basedLong-horizon agents whose path affects qualityScores the whole chain of plans, calls, tools, and handoffs as one trajectory

5. Agent metrics

Six metrics purpose-built for agents, spanning three layers of the agent loop.

LayerDoesMetrics
ReasoningPlans the task, picks a strategyPlan Quality, Plan Adherence
ActionSelects tools, generates argumentsTool Correctness, Argument Correctness
ExecutionRuns the full loop to a resultTask Completion, Step Efficiency
MetricScopeReferenceNeedsWhy it mattersCalculated as (plain language)
Plan QualityTrajectoryReferenceless• input (the task, from the golden) · plan read automatically from the traceCatches a flawed strategy before execution wastes effort following itReads the task + the plan from the trace; an LLM judge scores how logical and complete the plan is for that task. No plan detected → passes with score 1.
Plan AdherenceTrajectoryReferenceless• input · plan + execution steps, both read automatically from the traceA good plan means nothing if the agent drifts from it mid-runReads the task, the plan, and what actually ran; an LLM judge scores how closely execution stuck to the plan.
Tool CorrectnessComponent-levelReference-based• input · actual_output · tools_called (captured by tracing) · expected_toolsCatches wrong or missing tool calls, independent of answer qualityCorrect tool calls ÷ total tool calls, exact-match by default (name, args, output, or order — configurable strictness).
Argument CorrectnessComponent-levelReferenceless• input · actual_output · tools_calledRight tool, wrong arguments still breaks the taskCorrectly generated arguments ÷ total tool calls; an LLM judge checks the arguments against the input context, not a fixed expected value.
Task CompletionTrajectoryReferenceless• input (task — can be given or inferred) · outcome read automatically from the traceThe top-level pass/fail signal — everything else is diagnosticReads the task (given or inferred) + the final outcome from the trace; an LLM judge scores how fully the outcome satisfies the task.
Step EfficiencyTrajectoryReferenceless• input · every execution step, read automatically from the traceA working agent burning 3x the tokens/latency it needs isn't production-readyReads the task + every execution step; an LLM judge scores efficiency, penalizing redundant calls or loops not needed to finish the task.

Rule of thumb: trajectory metrics need the whole trace (evals_iterator(metrics=[...])); component-level metrics attach to one span — the LLM call that picks a tool and its arguments (@observe(metrics=[...])).

6. RAG metrics

Five metrics split across the two halves of a RAG pipeline — the retriever fetches chunks, the generator turns them into an answer — each targeting a specific hyperparameter.

ComponentHandlesMetrics
RetrieverFetches text chunks from the knowledge baseContextual Precision, Contextual Recall, Contextual Relevancy
GeneratorTurns retrieved chunks + query into an answerAnswer Relevancy, Faithfulness
MetricScopeReferenceNeedsTargetsCalculated as (plain language)
Contextual PrecisionRetrieverReference-basedretrieval_context, expected_outputRerankerChecks whether the reranker puts relevant chunks above irrelevant ones. An LLM judge compares chunk order against the ideal answer.
Contextual RecallRetrieverReference-basedretrieval_context, expected_outputEmbedding modelChecks whether retrieval captured everything the ideal answer needs. An LLM judge checks retrieval_context against expected_output for gaps.
Contextual RelevancyRetrieverReferencelessinput, retrieval_contextChunk size, top-KChecks what share of retrieved chunks are actually relevant to the input. An LLM judge scores each chunk and flags noise.
Answer RelevancyGeneratorReferencelessinput, actual_outputPrompt templateChecks whether the answer stays focused on the input. An LLM judge scores how directly actual_output addresses the question.
FaithfulnessGeneratorReferencelessactual_output, retrieval_contextThe LLM itselfChecks whether the answer sticks to what was retrieved. An LLM judge compares every claim in actual_output against retrieval_context for contradictions.

Same field, different job: Contextual Precision and Contextual Recall both read expected_output, but one checks ranking, the other checks completeness.

The RAG Triad

Answer Relevancy + Faithfulness + Contextual Relevancy are all referenceless — no expected_output needed. High scores across all three is a solid signal the pipeline's hyperparameters are dialed in, without any labeled data. Add Contextual Precision and Recall on top only when labeled outputs are available, for stricter retrieval checks.

Building the golden dataset

A golden is a lightweight template — just an input and an expected_output, not a full test case yet (no retrieval_context or actual_output; those get filled in live, at evaluation time, by actually calling the retriever and generator). Four ways to build the set, roughly in order of how much they scale:

MethodHow it worksScalable?
Human-writtenSomeone writes each input + expected_output by handNo — fine for a first handful of cases, too slow to sustain
LLM-assisted (chat UI) + human reviewGive a general LLM chat tool — ChatGPT, Claude — instructions/criteria to draft candidate goldens, then a person reviews and edits before useSomewhat — faster than by hand, but still manual glue: copy, paste, format, review
DeepEval SynthesizerThe inbuilt module that automates the same idea programmatically — generate_goldens_from_docs() generates goldens straight from your knowledge base, in code, at scaleYes — the automated version of the row above
From productionOnce the app is deployed, mine real user interactions from logs; thumbs-up/thumbs-down feedback decides what becomes a goldenYes, and the set keeps growing on its own
python
from deepeval.synthesizer import Synthesizer
from deepeval.dataset import EvaluationDataset

synthesizer = Synthesizer()
goldens = synthesizer.generate_goldens_from_docs(
    document_paths=["policy.txt", "handbook.pdf"]
)
dataset = EvaluationDataset(goldens=goldens)

On production feedback: a 👎 on a real response flags a genuine failure mode worth turning into a regression golden — the exact case that broke, kept so it never quietly breaks again. A 👍 is worth keeping too, as a known-good baseline to make sure future changes don't regress it. Either way, the golden set stays grounded in what users actually ask, not what the team assumes they'll ask.

7. G-Eval — custom criteria in plain English

What it's for: every other metric here checks one fixed thing — relevancy, faithfulness, tool calls. G-Eval lets you define your own criteria in a sentence or two — tone, safety, completeness, whatever the app actually needs — without writing a custom scorer from scratch. It's the metric Arena G-Eval below is itself adapted from.

How it works, in three steps:

  1. Generate steps

    Your plain-language criteria gets turned into a structured list of evaluation_steps (chain-of-thought).

  2. Judge

    An LLM judge scores the output against those steps.

  3. Score

    The steps are weighted by token log-probabilities into one final score.

Breaking one fuzzy criterion into several smaller steps is what makes this more consistent than just asking an LLM "rate this 1–5" directly — simpler sub-questions are easier for a judge to answer the same way twice.

criteria vs evaluation_steps — provide one or the other, never both:

criteriaevaluation_steps
SetupOne sentence; DeepEval generates the steps for youWrite the steps yourself
Best forEarly iteration — fast to try ideasA metric you've settled on — more stable, easier to fine-tune
Trade-offStep generation is itself probabilistic — slight run-to-run variationMore upfront effort, but consistent and directly tunable
python
from deepeval.metrics import GEval
from deepeval.test_case import LLMTestCaseParams

correctness_metric = GEval(
    name="Correctness",
    criteria="Determine whether the actual output is factually correct based on the expected output.",
    evaluation_params=[LLMTestCaseParams.ACTUAL_OUTPUT, LLMTestCaseParams.EXPECTED_OUTPUT],
)

The 7 most common G-Eval metrics

Going further, briefly:

  • Rubrics — instead of one blended score, define separate scored criteria with their own ranges (e.g. fluency 0–3, logical flow 0–3, linguistic flow 0–4) for more interpretable, fine-grained results.
  • DAG — for when a requirement is clear-cut rather than subjective, and needs a deterministic score every time. Covered next.

8. DAG — deterministic evaluation

A single LLM judge can be unpredictable when the rubric has several conditional rules. A DAG (Directed Acyclic Graph) makes those rules explicit: each node does one small task or decision, and every path ends at a score you chose. G-Eval gives one holistic judgement; a DAG gives control over exactly how each condition affects the score.

Use a DAG when the rubric has explicit branches:

  • "If a required fact is missing, score 0; otherwise judge quality"
  • "If the response violates policy, fail immediately"
  • "Classify the response into one of several known quality levels"

For one holistic judgement, use G-Eval — it takes minutes to set up. A DAG branch can also end in a G-Eval, so only the genuinely subjective part is left to a single judge.

NodeDoes
TaskNodePrepares evidence — extracts headings, claims, dates, tool names. Assigns no score; attach children with add_node(child)
BinaryJudgementNodeDecides one yes/no criterion — must define both a True and a False outcome
NonBinaryJudgementNodeClassifies into one of several unique string outcomes
DeepAcyclicGraphTakes the root nodes; validates the graph and rejects cycles

Every outcome you add with add_verdict(...) has exactly one destination:

  • score= (0–10) ends the path — converted to the metric's 0–1 score
  • then= a node or metric continues the path — another node, a GEval, or any other metric

Example: is a meeting summary correctly formatted?

Rules: all three headings (intro, body, conclusion) present, in the right order. Build it top-down — define the nodes, wire them, create the graph.

python
from deepeval.metrics import DAGMetric
from deepeval.metrics.dag import (
    DeepAcyclicGraph, TaskNode, BinaryJudgementNode, NonBinaryJudgementNode,
)
from deepeval.test_case import LLMTestCase, SingleTurnParams

# 1. Define the nodes
extract_headings = TaskNode(
    instructions="Extract all headings in `actual_output`",
    evaluation_params=[SingleTurnParams.ACTUAL_OUTPUT],
    output_label="Summary headings",
)
has_all_headings = BinaryJudgementNode(
    criteria="Does the summary contain all three headings: 'intro', 'body', 'conclusion'?",
)
correct_order = NonBinaryJudgementNode(
    criteria="Are the headings in the correct order: 'intro' => 'body' => 'conclusion'?",
)

# 2. Wire them top-down
extract_headings.add_node(has_all_headings)
extract_headings.add_node(correct_order)

has_all_headings.add_verdict(verdict=False, score=0)
has_all_headings.add_verdict(verdict=True, then=correct_order)

correct_order.add_verdict(verdict="Yes", score=10)
correct_order.add_verdict(verdict="Two are out of order", score=4)
correct_order.add_verdict(verdict="All out of order", score=2)

# 3. Create the graph and the metric
dag = DeepAcyclicGraph(root_nodes=[extract_headings])
metric = DAGMetric(name="Format Correctness", dag=dag)

test_case = LLMTestCase(input="<meeting transcript>", actual_output="<the summary>")
metric.measure(test_case)
print(metric.score)

One wiring detail: correct_order hangs off the task node because its criteria depends on the extracted headings, and it's also reached through the True verdict — a shared node, which runs once both parents are done.

Why hand off to G-Eval?

In the example above, a correctly ordered summary gets a fixed 10. But passing the format checks doesn't make a summary good — it can have perfect headings and still miss key points or make things up. A fixed 10 would give every well-formatted summary full marks, whatever it says.

Formatting is objective; quality is subjective. So split the work:

CheckHandled byWhy
Headings present, in orderDAG nodes with fixed scoresObjective — same answer every run
Is the summary actually good?A G-Eval at the endSubjective — no fixed number can capture it

To do that, swap the one verdict:

python
from deepeval.metrics import GEval

summary_quality = GEval(
    name="Summary Quality",
    criteria="How good is the actual output as a summary of the input?",
    evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT],
)

# structure is fine -> G-Eval decides the score
correct_order.add_verdict(verdict="Yes", then=summary_quality)

Now a summary with missing or misordered headings gets a fixed low score, and only a well-structured one reaches G-Eval.

Why LLM judges need this help

A few well-known failure modes explain why DAG, and several design choices already covered above, exist:

PitfallWhat happensHow it's handled here
Non-deterministicSame output can score differently across runsUse DAG for anything with a genuinely correct answer
Verbosity biasFavors longer answers over better onesWrite criteria that explicitly reward concision or penalize padding
Narcissistic biasA model may rate its own outputs slightly higherJudge with a different model than the one being tested, where practical
Coarse scoringReliable on broad calls, noisier on fine-grained scalesG-Eval's token-probability weighting smooths this out
Position biasIn pairwise comparisons, favors whichever answer came firstThis is exactly why Arena G-Eval blinds and randomizes position

9. Arena G-Eval — picking a winner

What it's for: every metric so far scores one output against a bar — a threshold decides pass or fail. Arena G-Eval answers a different question entirely: not "is this good enough" but "which of these is better." Hand it two or more "contestants" — different prompts, models, or configs run on the same input — and it names a winner instead of a score.

When to use it: comparing two prompt versions, two models (GPT-4 vs. Claude, say), or two configs on the same task — anywhere the real question is relative, not absolute. It's also more reliable than eyeballing two separate GEval scores side by side, since a per-output score carries its own noise; a direct head-to-head doesn't.

How it avoids bias: a blind, randomized-position, pairwise LLM-judge. Names and order are hidden and shuffled, so the judge can't just favor whichever answer happened to come first or ran longer.

No score, no threshold: it ranks rather than passing a bar. Read metric.winner and metric.reason, not a numeric score.

Regular metrics (e.g. GEval)Arena G-Eval
Question answeredIs this output good enough?Which output is better?
InputOne test caseMultiple contestants — same input, different outputs
ResultScore vs. thresholdWinner + reason
python
from deepeval.test_case import ArenaTestCase, LLMTestCase, SingleTurnParams, Contestant
from deepeval.metrics import ArenaGEval
from deepeval import compare

a_test_case = ArenaTestCase(
    contestants=[
        Contestant(name="GPT-4", hyperparameters={"model": "gpt-4"},
                   test_case=LLMTestCase(input="What is the capital of France?", actual_output="Paris")),
        Contestant(name="Claude-4", hyperparameters={"model": "claude-4"},
                   test_case=LLMTestCase(input="What is the capital of France?", actual_output="Paris is the capital of France.")),
    ]
)

metric = ArenaGEval(
    name="Friendly",
    criteria="Choose the more friendly response",
    evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT],
)

compare(test_cases=[a_test_case], metric=metric)

10. Non-LLM metrics

No LLM judge, no token cost, fully deterministic — same input always gives the same score. These check structure and exact matches, not meaning.

MetricChecksNeedsUse it when
Exact MatchIs actual_output identical, character-for-character, to expected_output?input, actual_output, expected_outputThere's exactly one right answer — labels, enum values, canned responses
Pattern MatchDoes actual_output fully match a regex pattern?input, actual_output + a patternOutput needs a shape, not exact text — emails, dates, phone numbers, IDs
Json CorrectnessDoes actual_output parse into a given schema?input, actual_output + an expected_schemaChecking structure — tool calls, function arguments, API responses
python
from deepeval.metrics import ExactMatchMetric, PatternMatchMetric, JsonCorrectnessMetric

ExactMatchMetric()                                        # exact string match
PatternMatchMetric(pattern=r"^[\w\.-]+@[\w\.-]+\.\w+$")  # regex match
JsonCorrectnessMetric(expected_schema=MySchema)           # schema match
  • Both are strict — full match only. A stray space or extra character scores 0. Pattern Match checks the whole output against the pattern (not "contains"), so wrap loose patterns in .*...* to match a fragment.
  • Json Correctness never judges content, only structure. An LLM is only called to explain why a schema failed — never to score it.
  • None of these fit open-ended output with many valid phrasings. Pair with an LLM-judge metric like Answer Relevancy instead.

11. Safety Metrics

All six are single-turn, LLM-judged, and referenceless — judged from the actual_output alone, no expected_output needed. The "What it checks" column below is each metric's own opening definition, since that line is the clearest statement of its purpose.

MetricWhat it checksNeedsCalculated as
BiasWhether the output shows gender, racial/ethnic, political, or geographical bias.input, actual_outputUnbiased opinions ÷ total opinions. An LLM extracts the opinions in the output, then classifies each as biased or not.
ToxicityHow toxic the output's tone is — personal attacks, mockery, hate, dismissiveness, or threats.input, actual_outputNon-toxic opinions ÷ total opinions, via the same extract-then-classify approach as Bias.
Non-AdviceWhether the output gives specific professional advice — financial, medical, legal, and similar — that it shouldn't.input, actual_output, advice_types (required)Appropriate advice statements ÷ total advice statements. Only advice within the listed advice_types is flagged — unlisted domains never fail.
MisuseWhether the output answers something outside a specialized chatbot's intended domain.input, actual_output, domain (required)Non-misuse statements ÷ total statements, judged against the stated domain.
PII LeakageWhether the output exposes personally identifiable or privacy-sensitive information.input, actual_outputNon-PII statements ÷ total extracted statements. Detects leaks during evaluation only — it doesn't redact or block them at runtime.
Role ViolationWhether the output breaks the character or role the assistant was assigned.input, actual_output, role (required)Binary: 1.0 if no violation is found anywhere in the output, 0.0 if even one is detected. No partial credit.
python
from deepeval.test_case import LLMTestCase
from deepeval.metrics import BiasMetric, ToxicityMetric, PIILeakageMetric
from deepeval import evaluate

test_case = LLMTestCase(
    input="Can you help me with my account?",
    actual_output="Sure! I can see your account details: John Smith, SSN: 123-45-6789.",
)

evaluate(
    test_cases=[test_case],
    metrics=[BiasMetric(), ToxicityMetric(), PIILeakageMetric()],
)

Non-Advice, Misuse, and Role Violation each need one extra required field that defines what "wrong" means for the app — without it, the metric has nothing to check against:

python
from deepeval.metrics import NonAdviceMetric, MisuseMetric, RoleViolationMetric

NonAdviceMetric(advice_types=["financial", "medical"])
MisuseMetric(domain="financial")
RoleViolationMetric(role="helpful customer service agent")
  • Higher is safer, for all six. Each score is the share of content that's not a problem, and the default threshold (0.5) is a minimum to clear, not a maximum.
  • Role Violation is binary, not a ratio — one out-of-character line drops the whole score to 0, unlike the others which average across multiple opinions or statements.

Telling the close ones apart:

  • Bias vs. Toxicity — prejudice against a group vs. a hostile tone. An output can be one without the other; many suites run both.
  • Non-Advice vs. Misuse — Non-Advice checks the content of an answer (does it cross into licensed-advice territory); Misuse checks the topic (did the bot answer something outside its domain at all).
  • Misuse vs. Role Violation — Misuse is about staying on-topic; Role Violation is about staying in character.
  • Role Violation vs. Role Adherence — Role Violation is single-turn and binary, gating one response; Role Adherence (covered above) scores persona consistency across a whole multi-turn conversation.

12. Multi-Turn Metrics

These check a whole conversation, not just one reply.

Chatbot conversations

MetricWhat it checksReferenceNeedsHow it's calculated
Role AdherenceDoes the chatbot follow its given role for the whole conversation?Referencelessturns, chatbot_roleNumber of assistant turns that followed the role, divided by the total number of assistant turns. An LLM checks each assistant turn against the chatbot_role, using earlier turns for context.
Turn RelevancyDoes the chatbot keep giving relevant replies as the conversation goes on?ReferencelessturnsNumber of turns with a relevant assistant reply, divided by the total number of assistant turns. It builds a group of recent turns (a sliding window) and checks if the last reply in that group fits with the turns before it.
Knowledge RetentionDoes the chatbot remember facts the user gave it earlier?ReferencelessturnsNumber of assistant turns without a forgotten fact, divided by the total number of assistant turns. An LLM pulls out facts from the user's turns, then checks each assistant turn for signs it forgot one.
Conversation CompletenessDoes the chatbot fully handle everything the user asked for?ReferencelessturnsNumber of user requests that were satisfied, divided by the total number of user requests. An LLM finds the user's requests from the user's turns, then checks if each one was met by the assistant.
python
from deepeval.test_case import Turn, ConversationalTestCase
from deepeval.metrics import RoleAdherenceMetric, TurnRelevancyMetric
from deepeval import evaluate

convo = ConversationalTestCase(
    chatbot_role="a 1920s detective",
    turns=[
        Turn(role="user", content="Can you help me find my missing dog?"),
        Turn(role="assistant", content="Ah, a case worthy of my talents. When was the mutt last seen?"),
    ],
)

evaluate(
    test_cases=[convo],
    metrics=[RoleAdherenceMetric(threshold=0.5), TurnRelevancyMetric(threshold=0.5)],
)

Agent conversations

MetricWhat it checksReferenceNeedsHow it's calculated
Goal AccuracyDid the agent plan and carry out steps well enough to actually reach the user's goal?Referencelessturns (can include tools_called)Average of two scores: how well the goal was reached, and how good the plan was, including whether it was followed.
Tool UseDid the agent pick the right tool and use it with the right arguments?Referencelessturns (with tools_called), available_toolsThe lower of two scores: whether the best tool was picked, and whether the arguments passed to it were correct. The argument score is only checked when a tool was actually called.
Topic AdherenceDoes the agent only answer questions on its allowed topics, and correctly refuse the rest?Referencelessturns, relevant_topicsNumber of correct answers and correct refusals, divided by the total number of question-answer pairs in the conversation.

Agent metrics need a bit more on the test case — the tools that were called, and the tools that could have been called:

python
from deepeval.test_case import Turn, ConversationalTestCase, ToolCall
from deepeval.metrics import ToolUseMetric, TopicAdherenceMetric
from deepeval import evaluate

convo = ConversationalTestCase(
    turns=[
        Turn(role="user", content="What's my order status?"),
        Turn(role="assistant", content="Let me check.", tools_called=[ToolCall(name="check_order_status")]),
    ],
)

evaluate(
    test_cases=[convo],
    metrics=[
        ToolUseMetric(available_tools=[ToolCall(name="check_order_status")], threshold=0.5),
        TopicAdherenceMetric(relevant_topics=["billing", "shipping"], threshold=0.5),
    ],
)

RAG conversations

The multi-turn versions of the single-turn RAG metrics covered earlier — same retriever-vs-generator split, scored per-turn using a sliding window instead of once.

MetricWhat it checksReferenceNeedsHow it's calculated
Turn FaithfulnessAre the assistant's claims across the conversation grounded in the retrieval context?Referencelessturns (each with retrieval_context)Groups turns into a sliding window (10 by default). For each window: pulls true statements from the retrieval context, pulls claims from the assistant's reply, checks each claim against those statements, then scores faithful claims ÷ total claims. Final score is the average across all windows.
Turn Contextual PrecisionAre useful retrieval context chunks ranked above the not-useful ones?Reference-based — needs expected_outcometurns, expected_outcomeFor each window, checks whether each retrieved chunk was useful for reaching the expected_outcome, and weights the score so chunks ranked higher count for more. Final score is the average across all windows.
Turn Contextual RecallDoes the retrieval context contain everything needed for the expected outcome?Reference-based — needs expected_outcometurns, expected_outcomeFor each window, breaks the expected_outcome into individual statements and checks how many can be traced back to the retrieval context, scoring attributable statements ÷ total statements. Final score is the average across all windows.
Turn Contextual RelevancyIs the retrieval context actually relevant to what the user asked?Referencelessturns (with retrieval_context)For each window, pulls individual statements out of the retrieval context and checks each one for relevance to the user's message, scoring relevant statements ÷ total statements. Final score is the average across all windows.
python
from deepeval.test_case import Turn, ConversationalTestCase
from deepeval.metrics import (
    TurnFaithfulnessMetric,
    TurnContextualPrecisionMetric,
    TurnContextualRecallMetric,
    TurnContextualRelevancyMetric,
)
from deepeval import evaluate

convo = ConversationalTestCase(
    expected_outcome="The chatbot must explain the store policies like refunds, discounts, etc.",
    turns=[
        Turn(role="user", content="What if these shoes don't fit?"),
        Turn(
            role="assistant",
            content="We offer a 30-day full refund at no extra cost.",
            retrieval_context=["All customers are eligible for a 30 day full refund at no extra cost."],
        ),
    ],
)

evaluate(
    test_cases=[convo],
    metrics=[
        TurnFaithfulnessMetric(threshold=0.5),
        TurnContextualPrecisionMetric(threshold=0.5),
        TurnContextualRecallMetric(threshold=0.5),
        TurnContextualRelevancyMetric(threshold=0.5),
    ],
)
  • The Reference column shows what a metric needs beyond turns — Referenceless means no expected_output/expected_outcome required.
  • Only assistant turns are checked in Role Adherence, Turn Relevancy, and Knowledge Retention. User turns are not scored directly.
  • Turn Relevancy and all four RAG conversation metrics check a turn against a group of earlier turns (a sliding window, 10 by default), not just the last message.
  • Turn Contextual Precision and Turn Contextual Recall both need expected_outcome — same field, different job: one checks ranking, the other checks completeness, same pattern as the single-turn RAG metrics above.
  • Tool Use needs available_tools — the full list of tools the agent could have picked from. Without it, the metric can't tell if a better tool existed.
  • Topic Adherence needs relevant_topics — the subjects the agent is allowed to answer. Refusing an off-topic question counts as correct, not as a failure.
  • All of these metrics can also be checked with a faster method instead of a full LLM call, if you want quicker results — set with deepeval set-eval-mode hybrid or system_one.

13. Running evals

Every eval needs a test case and a metric with a threshold to decide pass/fail; a dataset groups many test cases for a bulk run.

A test case passes only if every threshold-carrying metric passes. threshold=None still scores but doesn't gate; flaky=True warns instead of failing the run.

Dataset = a collection of goldens (test case templates). Synthesizer generates goldens straight from your own docs when you don't have a dataset yet.

Running a whole dataset (end-to-end) is the same loop every time: turn each golden into a test case, then evaluate the batch together.

python
from deepeval import evaluate
from deepeval.dataset import EvaluationDataset, Golden
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric

dataset = EvaluationDataset(goldens=[Golden(input="...")])
for golden in dataset.goldens:
    dataset.add_test_case(
        LLMTestCase(input=golden.input, actual_output=your_app(golden.input))
    )

evaluate(dataset, [AnswerRelevancyMetric()])

Component-level

Wrap any function with @observe(metrics=[...]) to score a nested span — a retriever, a tool, a sub-agent — instead of just the final output.

python
from deepeval.tracing import observe, update_current_span
from deepeval.metrics import AnswerRelevancyMetric
from deepeval.test_case import LLMTestCase

@observe(metrics=[AnswerRelevancyMetric()])
def complete(query: str):
    response = call_llm(query)
    update_current_span(
        test_case=LLMTestCase(input=query, actual_output=response)
    )
    return response

Trajectory-level

Score the complete ordered trace instead of one span. Needed for trajectory metrics (Plan Quality, Plan Adherence, Task Completion, Step Efficiency). Run with dataset.evals_iterator(metrics=[...]) instead of @observe.

python
from deepeval.tracing import observe
from deepeval.dataset import Golden, EvaluationDataset
from deepeval.metrics import TaskCompletionMetric

@observe(type="agent")
def travel_agent(user_input):
    flights = search_flights("NYC", "Paris", "2025-03-15")
    cheapest = min(flights, key=lambda x: x["price"])
    return f"Booked flight {cheapest['id']}"

dataset = EvaluationDataset(goldens=[Golden(input="Book the cheapest flight to Paris")])
for golden in dataset.evals_iterator(metrics=[TaskCompletionMetric()]):
    travel_agent(golden.input)
